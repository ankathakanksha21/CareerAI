# Step 0: accounts, saved data and removal of the demo persona

Date: 11 October 2026
Status: approved by the project owner on 11 October 2026; amended 12 October 2026 (section 18)
Branch: `live-features`

## 1. Why this step exists

The repo was built as a five-minute story demo around one fictional user, Aditi Rao. The AI and voice calls are real, but nearly all the data is seeded: one in-memory state shared by every visitor, wiped on restart, with a frozen date of 8 October 2026.

The product goal is different: a real career agent for international students and recent graduates in the UK, where every screen runs on the signed-in person's own data. Every later feature (real jobs, full CVs, tracker insights, streaks, networking, peers) stores per-user data, so accounts and a database come first.

**Goal of step 0.** Everything that is genuinely live today keeps working, but for a signed-in real person using only their own data. Anything that depended on fictional data is hidden until its own step makes it real.

## 4. What the user experiences

### 4.1 First visit

1. **Landing page.** Describes only features that are live. "Get started" opens sign-up. "Sign in" for returning users.
2. **Sign up.** Full name, email, password (minimum 8 characters), and a tick box agreeing to the privacy notice. If Supabase email confirmation is on, a "Check your email" screen follows; if off, the user is signed in immediately.
3. **Your details** (required before anything else):

   | Field | Input | Rule |
   |---|---|---|
   | Full name | Text, pre-filled from sign-up | Required |
   | University | Text | Required |
   | Course | Text, e.g. "MSc Business Analytics" | Required |
   | Graduation date | Month and year | Required |
   | Visa type | Student or Graduate | Required |
   | Visa end date | Date | Required |
   | Preferred locations | Up to 5 free-text tags, e.g. "London", "Remote" | At least 1 |

4. **Your background.** Talk to the coach (voice), or paste a CV or notes. The coach greets the user by first name and is told their course, university and visa type, so it asks about experience instead. This step can be skipped with "I'll do this later".
5. **Your profile.** The achievements just captured, each rewritten as a UK CV bullet, plus a two-sentence pitch.
6. **Your target roles.** AI-generated role families (direct fit, near fit, stretch). Each shows estimated overlap, typical UK job titles, what the user already evidences and what is missing. The user ticks 3 to 5 to target.
7. **Dashboard.**

A returning user who signs in lands on the dashboard. If "Your details" is incomplete they are sent back to it.

## 5. Architecture

```
Browser (React + Vite)
 ├─ supabase-js ───────────────► Supabase Auth   sign up / sign in / reset → short-lived access token
 ├─ /api/* + Bearer token ─────► FastAPI (one Vercel function)
 │                                 ├─ verifies the token against Supabase's public keys (JWKS)
 │                                 ├─ Postgres on Supabase, pooled connection   ← all user data
 │                                 ├─ Bedrock Mantle                            ← LLM
 │                                 └─ ElevenLabs API                            ← mints voice tokens
 └─ WebRTC audio ──────────────► ElevenLabs agents (coach, interviewer)
```

Principles:

- **FastAPI is the only gateway to user data and the only holder of secrets.** The browser talks to Supabase for login only.
- **The browser receives one Supabase value, the publishable key**, which Supabase designs to be public. It is served by `GET /api/config`, so there is still a single env file (`backend/.env`) and one set of Vercel variables.
- **Row-level security is on for every table with no policies.** Supabase auto-generates a REST API over public tables; deny-all RLS means the publishable key cannot read any of it. The backend connects as the database owner and enforces access in code.
- **Every data function takes a `user_id`.** There is no code path that queries user data without one.

## 6. Data model

All tables live in the `public` schema with row-level security enabled and no policies. Every table has `user_id uuid not null references auth.users(id) on delete cascade`, so deleting the login removes all of that person's rows. Primary keys are `uuid default gen_random_uuid()` unless stated. All have `created_at timestamptz not null default now()`.

### profiles (one row per user; `user_id` is the primary key)

| Column | Type | Notes |
|---|---|---|
| full_name | text not null | |
| university, course | text | |
| graduation_date | date | First day of the chosen month |
| visa_type | text | `student` or `graduate` |
| visa_end_date | date | |
| locations | text[] | 1 to 5 entries |
| pitch | text | Two-sentence networking pitch from the AI |
| updated_at | timestamptz | |

"Details complete" means university, course, graduation_date, visa_type, visa_end_date and at least one location are all set. The row is created on the user's first authenticated request, with the name from their sign-up.

### achievements

`title`, `raw` (their own words), `uk_version` (the UK CV bullet), `skills text[]`, `outcome`, `scale`, `context_note`, `source` (`voice` or `paste`).

### role_families

`name`, `fit` (`direct`, `near`, `stretch`), `overlap int` (0 to 100, an AI estimate and labelled as such), `uk_titles text[]`, `why`, `needs jsonb` (list of `{need, shown_by}` where `shown_by` is an achievement title or empty for a gap), `targeted boolean default false`. Unique on `(user_id, lower(name))`.

No salary or sponsorship fields. Those were model guesses in the demo; they return in step 2 computed from real listings and the sponsor register.

### saved_jobs

`title`, `company`, `location`, `url`, `description` (the pasted text, up to 20,000 characters), `summary` (AI, about 60 words), `keywords text[]`, `role_family_id` (nullable, set null on delete), `source` (`pasted` for now).

### cv_versions

`name` (e.g. "Product Analyst, Lumen Health v1"), `saved_job_id` and `role_family_id` (both nullable, set null on delete), `content jsonb` (profile paragraph, bullets, keywords, cover letter, gaps).

### stories

`achievement_id` (nullable, set null on delete), `title`, `competency`, `situation`, `task`, `action`, `result`, `strength`, `tip`.

### applications

| Column | Type | Notes |
|---|---|---|
| company, role | text not null | |
| role_family_id, cv_version_id, saved_job_id | uuid | Nullable, set null on delete |
| source | text | Company site, Referral, LinkedIn, Indeed, Graduate job board, University careers service, Recruiter, Other |
| stage | text | applied, no_response, rejected, screening, interview, rejected_after_interview, offer |
| applied_on | date | Defaults to today in Europe/London |
| posted_on | date | Nullable. Replaces "days after posting"; the gap is computed |
| job_url, contact, notes | text | Stored now; shown in the UI in step 4 |
| sponsor_licence | boolean | Nullable; filled from the register in step 2 |
| follow_up_on | date | Nullable; used in step 4 |
| updated_at | timestamptz | |

### journal_entries

`type` (`coach` or `interview`), `title`, `with_whom`, `summary`, `points jsonb`, `actions jsonb`, `scores jsonb` (nullable).

### usage_events

`id bigint identity`, `kind` (`ai` or `voice`), `action` (e.g. `tailor`, `interviewer`), `created_at`. Index on `(user_id, kind, created_at)`. Powers daily limits now and streaks in step 4.

### schema_migrations

`version text primary key`, `applied_at`. Written by `migrate.py`.

## 7. API

`GET /api/config` is public. Every other route requires a valid token and returns 401 without one.

### 7.1 Read

`GET /api/state` returns one object for the signed-in user:

```
{ profile, details_complete, achievements, role_families, saved_jobs, cv_versions,
  stories, applications, journal, stats, next_steps, content,
  usage: { ai: {used, limit}, voice: {used, limit} },
  config: { llm: bool, voice: {onboarding: bool, interviewer: bool} } }
```

Keeping a single read means the existing pages change little. If payloads grow, this is split per page later.

### 7.2 Writes (each touches one row, in one transaction)

| Route | Purpose |
|---|---|
| `PUT /api/profile` | Save "Your details" |
| `DELETE /api/account` | Delete the login and all data |
| `DELETE /api/achievements/{id}` | Remove a wrong achievement |
| `POST /api/families/{id}/target` | Tick or untick a role family |
| `POST /api/jobs`, `DELETE /api/jobs/{id}` | Add a pasted job, remove it |
| `POST /api/applications`, `PATCH /api/applications/{id}`, `DELETE /api/applications/{id}` | Tracker |

### 7.3 AI and voice (count against daily limits)

| Route | Result |
|---|---|
| `POST /api/ai/achievements` | Transcript or pasted text → achievements + pitch; journal entry |
| `POST /api/ai/families` | Achievements → role families (rules below) |
| `POST /api/ai/tailor` | Saved job + achievements → CV version (saved) |
| `POST /api/ai/star` | Achievement → STAR story (saved) |
| `POST /api/ai/interview-feedback` | Transcript → scores and feedback; journal entry |
| `POST /api/ai/tone` | Decode or rewrite a phrase |
| `POST /api/ai/diagnosis` | Weekly review from tracker stats |
| `GET /api/voice/token` | Mint an ElevenLabs token (counts as a voice session) |
| `GET /api/voice/transcript/{conversation_id}` | Fallback transcript, only for the session's owner |

`POST /api/jobs` also makes one AI call to summarise the description and match it to one of the user's role families. If that call fails the job is still saved, with the first 300 characters as its summary and no family.

**Refreshing role families.** Families are matched by name, ignoring case. Existing ones are updated in place (keeping their id and their "targeted" tick), new ones are added, and a family is removed only if it is untargeted and no application, CV version or saved job points to it.

Removed routes: `/api/reset`, `/api/tasks/*`, `/api/families/select`, `/api/contacts/*`, `/api/events/*`, `/api/peers/*`, `/api/buddies/*`, `/api/ai/outreach`, `/api/ai/peer-notes`, `/api/ai/evidence` (renamed).

### 7.4 Next steps on the home page

Computed on every read, never stored.

| Order | Step | Done when |
|---|---|---|
| 1 | Build your profile | At least 1 achievement |
| 2 | Pick your target roles | At least 1 targeted role family |
| 3 | Add a job you want | At least 1 saved job |
| 4 | Tailor a CV for it | At least 1 CV version |
| 5 | Practise an interview | At least 1 interview journal entry |
| 6 | Log your first application | At least 1 application |

"Your next best step" is the top tracker finding if one exists, otherwise the first step not yet done. The richer weekly plan arrives in step 4.

### 7.5 Diagnosis rules on real data

| Rule | Change from the demo |
|---|---|
| Low reply rate for a role family (4 or more applications, under 15%) | Unchanged. CV versions compared by id |
| Interviews but no offers (3 or more interviews, 0 offers) | The hard-coded fictional company name is removed from the advice |
| Referrals work but are rarely used | Unchanged; job-board sources updated to the new source list |
| Few visa-ready roles in a family | Removed until step 2, when real jobs and sponsor data exist |
| Slow applications | Uses `applied_on - posted_on`; applications without a posted date are left out |

All rules return nothing on an empty tracker.

## 8. AI layer

- **No canned fallbacks.** Each `ai.*` function returns the model's result or raises. The route answers 502 with a plain message and the page shows Retry. Nothing is saved from a failed call.
- **One automatic retry** when the model returns malformed JSON or omits a required field.
- **Fallback model.** If the primary model answers 403 or 404 and `BEDROCK_FALLBACK_MODEL_ID` is set, the same request is tried once on the fallback.
- **Reasoning output.** The configured model (`qwen.qwen3-235b-a22b-2507`) can emit a `<think>` block. It is stripped before JSON parsing.
- **Prompts use the profile**, not the old persona: name, course, university, visa type and visa end date.
- The "never invent employers, numbers or achievements" rule in the base prompt stays.
- Removed prompt functions: outreach and peer notes (rebuilt in steps 6 and 7).

## 9. Voice

- `setup_agents.py` keeps creating two private agents. The coach prompt gains the variables `course`, `university` and `visa_type`, and stops asking for them. It still asks what each overseas employer does and pushes once for a number.
- Each session is started with the user's id as a dynamic variable. The transcript fallback route returns a transcript only when the stored conversation carries the caller's id.
- The interviewer receives the saved job's title, company and summary, or a generic brief for "General practice".
- The existing WebRTC-then-WebSocket fallback stays. The automatic WebSocket retry of the same attempt does not count as a second session.

## 10. Daily limits

| Setting | Default | Counts |
|---|---|---|
| `DAILY_AI_LIMIT` | 40 | Every call to an `/api/ai/*` route and the summary call in `POST /api/jobs` |
| `DAILY_VOICE_LIMIT` | 3 | Every voice session started |

A day runs midnight to midnight, Europe/London. Over the limit the route answers 429 and the page shows "You've reached today's limit. It resets at midnight." The account menu shows usage. Voice calls are also capped at 7 minutes each by the agent configuration, as today.

## 11. Security and privacy

| Concern | Handling |
|---|---|
| Authentication | Supabase Auth. Passwords never reach our backend |
| Token verification | Signature checked against the project's JWKS (ES256 or RS256), keys cached. `exp`, `iss` and `role = authenticated` checked. If a token is signed with the legacy shared secret (header `alg` is HS256, which older projects use), it is validated by asking Supabase's `/auth/v1/user` and caching the answer until the token expires. Supabase advises against checking shared-secret tokens locally |
| Authorisation | Every query filters by the caller's `user_id`. Automated tests prove account A cannot read, change or delete account B's rows |
| Direct database access from browsers | Blocked by deny-all row-level security |
| Secrets | Only in `backend/.env` (git-ignored) and Vercel project settings. The Supabase secret key is used for one thing: deleting a login |
| Data location | Supabase project in London. The LLM runs in `us-east-1` and ElevenLabs processes audio outside the UK; the privacy notice says so |
| Right to erasure | "Delete my account" removes the login; cascading foreign keys remove every row |
| Transparency | A draft privacy notice lists what is collected, why, who processes it and how to delete it. **It is a draft and must be reviewed before any public launch** |
| Consent | Tick box on sign-up; a line beside "Start talking" says the call is processed by ElevenLabs |
| Immigration content | Step 0 shows only the user's own visa end date and a countdown. It gives no visa advice. Rules and thresholds arrive in step 2 after checking gov.uk, with a "not immigration advice" note |
| Cost abuse | Daily limits per user |

## 14. Testing

**Automated (pytest, backend).**

- `auth`: accepts a valid token; rejects expired, forged, wrong-issuer and non-authenticated tokens. Uses a key pair generated in the test.
- `repo`: every table's create, list, update and delete, run against the development database inside transactions that are rolled back.
- **Isolation**: for every read and write function, user B gets nothing and changes nothing belonging to user A.
- `limits`: under, at and over the cap; the London day boundary.
- `analytics`: empty data returns no findings and no errors; each rule fires on data built to trigger it; next steps follow the table in 7.4.
- `ai`: output shaping, the retry on malformed JSON, `<think>` stripping, fallback model on 403/404. The model itself is stubbed.
- Routes: 401 without a token on every route except `/api/config`.

**Live checks with real keys (run once, results recorded).** One real call per AI route on the configured model; one voice session with each agent.

**End to end in the browser.** Sign up → details → onboarding by paste → target roles → add a job → tailor a CV → mock interview feedback → log an application → sign out → sign in and see the same data → sign up a second account and confirm it is empty → delete the first account.

Frontend has no test runner today and little pure logic; it is verified through the end-to-end run. A runner is added when a step introduces logic worth unit-testing.

## 16. Trade-offs

| Decision | Gain | Cost | Revisit when |
|---|---|---|---|
| FastAPI as the single gateway | One place for logic and security; secrets stay server-side | One extra network hop per request | Real-time features are needed |
| Plain SQL, no ORM | Few dependencies, fast cold starts on Vercel, every query visible in one file | Queries written by hand | The schema passes roughly 20 tables |
| One `/api/state` read | Small frontend change now | Payload grows with the user's history | A user has hundreds of rows |
| Deny-all RLS, checks in code | Simple mental model; one enforcement point | RLS is a backstop, not per-user defence in depth | The browser ever needs direct Supabase reads |
| LLM in `us-east-1` | Uses the key and model already available | Personal data is processed outside the UK | A UK or EU model is available on the account |
| One Supabase project for development and live | Simple | Test data sits beside real data | Before a public launch |
| Email confirmation off | Sign-up works without an email provider | Unverified emails; password reset still depends on the limited mailer | Before a public launch |
| Removing canned AI fallbacks | Users never see invented content | A model outage shows an error instead of something plausible | – |
| Hiding unbuilt pages | Nothing fake, minimal UI | The app looks smaller until later steps land | Each step restores its page |
| Usage counted per attempt | Simple, protects the bill | A failed call still uses one of the day's 40 | Users hit limits because of failures |

## 17. Definition of done

- Two different accounts can sign up, onboard and use every page in section 4.2, and neither can see the other's data.
- Data survives a backend restart and a sign-out.
- No fictional person, company, job, date or canned AI answer appears anywhere in the app or the codebase.

**12 October 2026, requested by the project owner: show that the user's voice was actually heard.**
